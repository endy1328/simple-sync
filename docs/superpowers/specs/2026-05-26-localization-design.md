# simple sync Localization Design

## Goal

Add a first-pass localization system for `simple sync` so the app can display its UI in Korean and English without changing internal sync behavior or config compatibility.

The first supported languages are:

- `ko-KR`
- `en-US`

The design should keep implementation small enough for the current WinForms codebase, where UI controls are created manually in code rather than through the Visual Studio designer.

## Scope

Localization applies to user-facing application text:

- Main window title, header, toolbar labels, buttons, combo-box display labels, grid column headers, status bar text.
- Activity section labels, activity filter labels, selected-pair status text.
- Sync mode display names such as `Copy changes` and `Mirror source`.
- Filter dialog title, help text, field labels, button text, preset tooltip text when owned by the app.
- Folder browser descriptions.
- Activity log messages generated by the app.
- Validation and error messages generated by the app.

The following are out of scope for the first pass:

- Translating `README.md`; it remains Korean per project rule.
- Translating user-provided pair names, paths, config values, or file names.
- Translating persisted mode values such as `copy` and `mirror`.
- External user-editable translation packs.
- Full right-to-left language support.

## User Experience

The main window will include a `Language` selector in the toolbar near the existing `Skin` selector.

Changing the language should:

- Update visible labels immediately.
- Save the selected language to `config.toml`.
- Keep the current sync pairs, logs, progress, skin, and interval unchanged.

Startup behavior:

- If `config.toml` contains `language`, use it.
- If absent or unsupported, use `ko-KR` as the default for now.
- Future OS-language auto-detection can be added later without changing the localization API.

## Config

Add a top-level config key:

```toml
language = "ko-KR"
```

Rules:

- `ko-KR` and `en-US` are supported.
- Unsupported values fall back to `ko-KR`.
- Existing config files without `language` continue to load normally.
- Saving the config writes the selected language.

## Architecture

Use a lightweight custom localization service instead of WinForms `.resx` designer resources.

Rationale:

- The UI is built manually in `MainForm.cs` and `FilterDialog.cs`.
- Most strings are assigned in code, not designer metadata.
- A key-based service is easier to apply incrementally and test with the current structure.

### New Types

`LanguageOption`

- `Code`: `ko-KR`, `en-US`
- `DisplayName`: visible name in the language selector

`LocalizationService`

- Owns the current language code.
- Provides `Text(string key)` for simple strings.
- Provides `Format(string key, params object[] args)` for formatted strings.
- Falls back to `ko-KR`, then to the key itself if a translation is missing.
- Exposes supported language options.

`LocalizedStrings`

- Static dictionaries for `ko-KR` and `en-US`.
- Key names should be stable and grouped by area:
  - `app.title`
  - `toolbar.sync_now`
  - `grid.source`
  - `activity.no_targets`
  - `filter.extensions.label`
  - `log.completed`

## UI Application

### MainForm

Add a private localization service field and a language ComboBox.

Add an `ApplyLanguage()` method that sets:

- Window title.
- Header title/subtitle.
- Toolbar labels and buttons.
- Skin and language labels.
- Grid column headers.
- Activity header and filter labels.
- Status bar text.
- Mode ComboBox display labels.

Do not rebuild the whole form when language changes. Update existing controls in place and refresh the grid.

### Mode Display

Keep persisted values as `copy` and `mirror`.

Display names come from localization:

- `copy`: Korean `변경 파일 복사`, English `Copy changes`
- `mirror`: Korean `소스 미러링`, English `Mirror source`

### FilterDialog

Pass `LocalizationService` or the selected language into the dialog.

Localize:

- Dialog title.
- Intro text.
- Quick preset description.
- Field labels, hints, and tooltip text.
- `Include subdirectories`.
- `Reset`, `Cancel`, `Apply`.

Preset names remain config-driven. If the user changes preset names in `config.toml`, the app displays them as written. Built-in default preset names should be localized only when defaults are created by the app.

## Activity Logs

New log messages should use localization keys.

Existing logs already in the text box should not be rewritten when the language changes. This avoids confusing history and keeps implementation simple.

Examples:

- Korean: `[Pair 1] 완료: 복사 1, 유지 2, 삭제 0, 제외 3, 실패 0`
- English: `[Pair 1] Done: copied 1, skipped 2, deleted 0, excluded 3, failed 0`

## Testing

Add focused tests for:

- Unsupported language fallback.
- `AppConfig.Language` load/save round trip.
- Mode labels for both languages.
- Selected-pair status formatting for both languages.
- Missing localization key fallback.

Manual verification:

- Start with no `language` in config and confirm Korean default.
- Switch to English and confirm toolbar, grid, status, filter dialog, and activity filters change.
- Restart and confirm English is restored.
- Switch back to Korean and confirm config updates.
- Confirm sync behavior does not change.

## Migration

Existing configs remain valid.

On first save after the localization change, config will gain:

```toml
language = "ko-KR"
```

No existing pair data or filter presets should be modified except normal config formatting behavior already present in the app.

## Risks

- Missed hard-coded strings may leave a mixed-language UI.
- Layout may need width adjustments for longer English or Korean strings.
- Log localization may touch many call sites; implement incrementally and keep tests around format helpers.
- Dynamic values such as paths and user pair names must never be translated.

## Recommended Implementation Phases

1. Add config and localization service with tests.
2. Localize main window static UI and mode display.
3. Localize status text and activity helper formatting.
4. Localize filter dialog.
5. Update docs and manual harness.
6. Bump version for the user-facing feature.
